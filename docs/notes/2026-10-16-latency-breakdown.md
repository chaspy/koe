# 「出力まで若干遅い」の内訳（BUG-4）

利用者の声「出力まで若干遅い」について、遅いのが Mac の負荷のせいか、Koe の処理のせいかを切り分けた。
使ったのは chaspy の `history/*.json` の時間・負荷・長さの数値と、`events.jsonl` の `enter_scheduled` / `server_restart` だけ（録音と文字起こしの本文は見ていない）。
期間は 10/13 10:45（離して→貼るの計測を入れた版）〜 10/16 22:22。貼れた発話 480 件。集計は `koe_eval.py perf` の「段階別・条件別」で出せる。

## 段階と記録の有無

| 段階 | 記録 | 中身 |
|---|---|---|
| キーを離す → Koe が受け取る | `key_up_lag_ms`（171 件） | 中央 0 / p90 1 ms。効いていない |
| 録り足し | `stop_ms` | 語尾の切れ対策で離した後 0.25 秒録る（固定）＋録音の確定 |
| プロンプト作り | `prompt_ms`（10/15 10:40 の版から） | whisper に渡す用語・直前の文 |
| 文字起こし | `transcribe_ms` | whisper-server の応答まで（やり直しを含む） |
| その他 | 記録なし（差し引きで出す） | 離して→貼る から上の 3 つを引いた残り。辞書の置き換え・繰り返しの判定・貼り先の確認と、メインスレッドの待ち |
| ⌘V を送る → 画面に出る | 記録なし | 貼り先のアプリ側の時間 |
| 貼る → Enter | `events` の `enter_scheduled.delay_ms`（発話とは結び付いていない） | 自動送信のときだけ。負荷に応じて延ばしている |

負荷は `load1`（1 分平均。この Mac は 12 コア）。全期間の分布は 10% 点 6、中央 9.3、90% 点 24.6。

- 前の版で「その他」が 1 秒を超えた発話は 39 / 298 件（13%）。今の版では 2 / 182 件。2 件は whisper の起こし直し（10/16 10:51、`server_restart`）と、負荷 252 のとき（10/15 14:01、離して→貼る 37 秒）。
- 離して→貼るが 2 秒を超えた発話は、前の版 43 / 298 件（14%）、今の版 7 / 182 件（4%）。今の版の 7 件のうち 5 件は音声が 28〜88 秒、残りは上の 2 件。
- 文字起こし（音声 15 秒未満に絞る）は負荷でほとんど変わらない: 今の版で負荷 < 8 が 495 / 608、8〜16 が 509 / 616、>= 16 が 524 / 604。
- 同じく音声 15 秒未満で、前の発話から 10 分以上あいた後の文字起こしは 909 / 1109（8 件）。1 分未満は 493 / 596、1〜10 分は 516 / 597。
- 文字起こしは音声の長さに比例して延びる。今の版で音声 5 秒未満 465 / 562、5〜15 秒 540 / 645、15〜30 秒 656 / 882、30 秒以上 1385 / 1941。
- 録り足しは 0.25 秒固定＋確定で、中央 290 前後。負荷 >= 16 では p90 が 543 に延びる。
- 裏で改善ループが動いていた発話は 17 件で、離して→貼るは 1009 / 1910（全体と大差なし）。
- 自動送信の Enter までの待ち（貼ったあと）は 552 / 1067 ms（163 回）。離して→貼るには含まれない。待ちは `0.25〜0.5 秒 ×（1 + (負荷 − 4) / 10）` で、負荷 16 なら 2.2 倍になる。

## 結論

- **「若干遅い」の主因は Koe の処理だった。** 前の版では、10 分以上あいた後の最初の発話で、文字起こしの前に用語の使用回数を数える処理が 3〜4 秒かかっていた（その他 2981 / 3845）。これは 9ee4a9e（10/15 10:33、裏で数えるように変更）で直っていて、今の版の 10 分以上あいた後の その他 は 58 / 277。p90 は 2273 → 1466 に下がった。
- **今の版の内訳（中央 906）は、録り足し 290（うち 250 は固定）＋文字起こし 534＋プロンプト 10＋その他 51。** 残りの大半は whisper の時間で、Koe の後処理（その他）は 50 ms 前後。
- **Mac の負荷の影響は小さい。** whisper の時間は負荷でほぼ変わらない。負荷 >= 16 で中央が 864 → 1122 に延びるが、その差は録り足し・プロンプト・その他（メインスレッドの待ち）に分かれて出ていて、各段階で数十 ms ずつ。極端な負荷（252）のときだけ数十秒になる。
- **今残っている遅い発話は、主に長い発話（30 秒以上で 1.9 秒前後）。** 次が 10 分以上あいた後の文字起こしで、短い発話でも 0.5 秒 → 0.9 秒になる。

## 推測（確かめていない）

- 10 分以上あいた後に whisper が遅いのは、GPU（Metal）の省電力状態からの立ち上がりか、モデルのメモリが退避されたことによると考えられる。件数が 8 件と少なく、原因を切り分ける記録は無い。
- 自動送信を使っているとき、利用者が「出力」と感じるのは Enter で送られた時点かもしれない。その場合、Enter までの待ち 0.55〜1.07 秒が上乗せされて見える。負荷が高いほどこの待ちが延びる。

## 次の一手の候補

1. 10/15 10:40 以降の版で、利用者にもう一度体感を聞く。主因はすでに直っている。
2. 10 分以上あいた後の遅れが気になるなら、しばらく使っていないとき（押した瞬間など）に whisper-server へ空の短い音声を投げて温める。効果は記録（`transcribe_ms` の 10 分以上あいた後の行）で確かめる。
3. 自動送信の Enter 待ちを発話の記録に残す（`enter_delay_ms`）と、「送られるまで」の体感と照らし合わせられる。今は events にだけあり、発話と結び付いていない。
